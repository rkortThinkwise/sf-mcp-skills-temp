# Writing dynamic model code (meta control procedures)

Dynamic model code is SQL that runs during **model generation itself**, expanding the model (adding
columns/tasks/security/etc. across every matching object) — distinct from regular control
procedures, which generate application-level program objects. Not for user-specific requirements;
avoid dependencies between what it generates and hand-modeled objects, since the two regenerate on
different triggers.

Three automatic parameters: `@model_id`, `@branch_id` (support imported base models with different
naming), `@control_proc_id` — stamp this into the "Generated by control procedure" field on every
row created, so ownership is traceable and safely regenerable/retirable later.

### rdbms_type — when it's actually required
Since 2026.2, multi-RDBMS models exist. `prog_object`, `prog_object_parmtr`, `prog_object_item`, and
`prog_object_item_parmtr` carry an `rdbms_type` column tagging which platform a row belongs to:
`0` SQL Server, `1` DB2 iSeries, `3` Oracle, `4` PostgreSQL. Single-RDBMS models get it auto-filled.
**Required explicitly** only when a SQL-assigned/dynamic model procedure on **Delete** or
**Fully managed** strategy inserts directly into those four tables in a multi-RDBMS model — omit it
there and the insert errors. Harmless to set always, even single-platform. On **Staged**, treat
`rdbms_type` as just another staging-table column to populate, not something inferred for you.

This requirement is not unique to these four tables — see "Calculated columns — and a wider 2026.2
`_query`-split pattern" below for the much broader family of `<entity>_query` companion tables that
need the same treatment.

To emit different generated dialects for the same logical object, insert one `#prog_object_item`
row per `(object, rdbms_type)` pointing at a dialect-specific template — never make one template's
literal text valid on two engines through escaping tricks.

**Fan-out source matters: `branch_rdbms_type`, not `branch`.** When a dynamic-model procedure needs to
emit one row per enabled platform (not just correctly populate the `rdbms_type` key on an otherwise
single row), source the fan-out from `branch_rdbms_type`, not `branch`. `branch` always returns
exactly one row per branch regardless of how many platforms are enabled, so a generator written as
`... from branch pv where pv.model_id = @model_id and pv.branch_id = @branch_id` silently produces
only one platform's row even in a genuinely multi-RDBMS model — no error, just quietly incomplete.
Verified live: two production dynamic-model procedures generating per-column domains needed rewriting
from `from branch pv` to `from branch_rdbms_type brt` (same `model_id`/`branch_id` filter) to correctly
fan out one row per enabled `rdbms_type`.

### The tag-driven pattern (verified in production models)
Combine a **tag** (a free-form property attachable to any model row) with a Staged dynamic-model
procedure: check for an opt-out tag on the target before adding the generated object, so specific
tables/columns can be excluded. Real examples seen in production:
- `Active_Col` — adds an `Active` column to every table with an `Update_Hash` column, skippable via
  a `No_Active_Col` tag.
- `Active_Prefilter` — adds an `Is_Active` prefilter to every table with that `Active` column,
  skippable via `No_Active_Prefilter`.
- `Customer_Prefilter` — adds a `My_Customer` prefilter to every table with a column on the
  `Customer_Code` domain, skippable via `No_My_Customer_Prefilter` — a real multi-tenant row-security
  rollout with a per-table escape hatch.
- A check-constraint-message generator that loops over every CHECK constraint and inserts a
  translated `#msg` row (`msg_id`, `msg_description`, `msg_location_id = 'popup'`,
  `msg_regular_expression` capturing the raw DB error) automatically, instead of hand-modeling one
  message per constraint. A `msg` row created this way is itself a translatable object (see
  `thinkwise_software_factory_translation_objects`) — the dynamic-model procedure inserting `#msg`
  rows should also generate (or a follow-up pass should fill in) the corresponding
  `transl_object_transl` text, or the constraint message renders as a bracket-placeholder
  (`[msg_id]`) instead of real text the first time it fires.

All of these open by `declare`-ing the tag id and target object names as local variables before
touching anything — copy that structure: name every knob before using it. Signal to reach for
dynamic model code at all: the moment "every X needs a Y" shows up twice.
